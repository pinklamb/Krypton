How it works

What Krypton measures, and what it does with it

Krypton reads each file as a syntax tree, measures how heavy every function and file is to read and change, and turns that into flags, hints and a purity score.

The pipeline

  1. Parse. Each file becomes a syntax tree. Files that cannot be parsed, or are too large to parse safely, are reported instead of guessed at.
  2. Walk. One depth-first pass over the tree records every decision, how deeply it is nested, effective size and the variety of outputs, function by function. The next section shows how this works.
  3. Rate. Krypton combines those measurements, and how files depend on each other, into a structural rating per function and per file.
  4. Flag. Functions and files over the limit are flagged, with a reason: tangled logic, an overloaded function, an overloaded file, a coupling hotspot, or a file that could not be parsed.
  5. Advise. For each heavy function Krypton names the deepest decision and the block most worth extracting, and predicts the effect.
  6. Track. With a history file, Krypton compares each run with the last and explains why a function did not improve.

How the score is calculated

The starting point: radon

Krypton's score is modeled after radon, the standard cyclomatic-complexity tool for Python. Every decision in a function (an if, a loop, a case, a catch, a boolean operator, a ternary) adds one more path through the code, so the more decisions, the more paths a reader or an agent has to hold in mind. Krypton counts the same decisions radon counts. For JavaScript and TypeScript it applies the same rules, checked against ESLint's complexity rule. Both were compared on about 16,500 files with no mismatches.

Radon stops at the count. It reports the same number whether three decisions sit side by side or are stacked three levels deep, but those two functions are very different to read and to change. Krypton's addition is where each decision sits, and it finds that with a depth-first walk.

The depth-first walk

Krypton parses each file into a tree: file, then functions, then statements, then expressions. It then walks that tree once, keeping a stack (a to-do list where the newest item is handled first) of the places it still has to visit, each tagged with how deep it sits.

  1. Start at the top of the file at depth 0, with the root on the stack.
  2. Take the newest item off the stack and look at it. If it is a decision, record it together with its current depth.
  3. Push its children onto the stack, each tagged with the depth it will sit at. The body of an if, a loop, a catch or a case is one level deeper; statements next to each other stay at the same level.
  4. Repeat. Because the newest item always comes off first, Krypton follows one branch all the way down to its deepest point, then backs up and takes the next sibling that was waiting. That is what depth-first means.
  5. Open and close scopes. Entering a function opens a scope; a marker left on the stack closes it when the walk has finished everything inside, and the totals are credited to that function. A function inside a function is accounted for in its own scope.

Here is a small function and the walk through it:

def pay(order):
    if order.paid:
        for item in order.items:
            if item.taxable:
                add_tax(item)

Radon reports this function as complexity 4 (one, plus three decisions). It would report 4 again if the three ifs sat one after another. Krypton records the same three decisions and also that here they are stacked three deep, where in the flat version each would sit at depth 1. A decision nested deeper makes the function harder to follow than the count alone suggests, and Krypton's rating takes that into account.

Why a walk like this

  • One pass. Everything is gathered as the walk goes, so the cost grows in step with the size of the file.
  • No recursion. The stack is explicit, so a deeply nested or very large file cannot overflow the call stack.
  • Flat memory on huge inputs. A list or object with thousands of entries is walked one entry at a time, so memory stays constant.
  • Comprehensions count like the loops they stand for. [f(x) for a in b if c] is scored as a loop with an if inside, so tucking logic into a one-liner does not hide it.

From the walk to the rating

When the walk finishes a function it has its number of decisions, its deepest level, a nesting-aware total in which a decision counts for more the deeper it sits, its effective size and the variety of its outputs. Krypton's scoring algorithm combines those into the function's rating, and rolls functions up into the file's rating. Over the limit, the function or file is flagged. The exact weights and the rating formula are not published.

What else it measures

Decisions

Conditions, loops, cases, catches, boolean operators and ternaries, counted as radon and ESLint count them.

Nesting

How deeply decisions are stacked, found by the depth-first walk above.

Effective size

Long or multi-statement lines count for more than short ones, so packing code onto fewer lines does not help.

Coupling

A file wired to many others, through imports or a shared global object, is flagged so the wiring gets split instead of piling into a few core files.

Trivial wrappers

Splitting code into many tiny functions just to stay under a limit lowers the purity score. Krypton is meant to reward real structure, not shuffling.

What is not published

The exact weights, the rating formula and the file-ordering algorithm are proprietary. What you can rely on:

  • Decision counts match radon and ESLint.
  • It resists the obvious ways to game a complexity score: packing lines, giving every branch a different return value, and spreading one heavy function across helpers in the same file.
  • Limits were calibrated on thousands of real library files, so well-written code is rarely flagged.
  • The ordering of files for prompt caching never changes a score.

Flags and the purity score

Each flagged file carries a reason in the JSON output: semantic_path_logic, function_overload, file_overload, coupling_hotspot, unparseable or concentration_rule. The purity score summarizes the whole run from 0 to 100.

Use --level relaxed to clear the worst offenders first, then tighten to standard or strict.

Refactoring hints

When a function is over the limit or nested three levels deep, Krypton says where and what to try:

m.py:1 tangle: deepest decision at line 5 (depth 4), inside lines 4-8 which hold most of this
function's decision weight; invert conditions with early returns, or move lines 4-8 into a helper

When a hint names a block it also predicts the ratings after extracting it. Hints are advice only and never change a score.

Progress and stalls

With --history FILE.jsonl every run is logged and compared with the last:

Progress since the last run:
  purity: run 4: purity 41 -> 55 -> 55 -> 60; flagged files 5 -> 4
  src/game.js:update: improved 4840 -> 2100 (57% lower)
  src/game.js:render: STALLED for 3 runs: the hinted block is still intact; the edits were elsewhere

A function that did not improve says why: not edited, the block it was told to extract is untouched, the weight moved to another function, or the block changed without helping. The log keeps ratings, names and line hashes only, never source code.

Ordering files for prompt caching

If your tool sends the whole codebase on every turn, the files that rarely change should come first, so that most of the prompt is identical from one turn to the next and the provider can reuse it. Krypton orders your files from most stable to most volatile using their change history. This is a prediction from history, not a guarantee: across 20 open-source repositories it reused more of the prompt than alphabetical order on 12 and less on 7, so check it on your own repository. Local and private

The command-line tool runs entirely on your machine and makes no network calls. The history log never stores source code.

Limits

  • It measures structure, not correctness or style. It will not catch a bug.
  • Files that are too large, contain extremely long lines (minified bundles) or are extremely wide are not analyzed. They are left out of the score and listed with the setting that would include them, never silently.
  • Token counts and dollar figures are estimates.
  • No import-cycle detection yet.
