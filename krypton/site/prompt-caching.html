Prompt caching

Cut the cost of re-reading your code

Coding agents send your codebase to the model on every turn. Providers bill text they have already seen at a fraction of the normal price, so the longer the unchanged part stays at the front of each request, the smaller the bill.

The short version. On garth, ordering files by change history made the same prompts 35% cheaper. Across 20 real repositories it beat alphabetical order on 12 and lost on 7, a typical gain of about 4 points of cache reuse, so how much you save depends on your repository.

How caching rewards order

Providers cache the longest identical prefix of a request. If a file near the start changes, everything after it has to be read again at full price. If only files near the end change, almost the whole request is reused.

So the best order puts the files that rarely change first and the ones that change often last.

Krypton's ordering

$ krypton src --order-by-volatility
# JSON: files from most stable to most volatile, with a token estimate for each

Krypton's ordering algorithm uses each file's change history. Build your prompt from the files in that order. You can supply your own change counts with --volatility counts.json. The ordering is a hint from history, not a guarantee, and it never changes a score.

Measured results

We replayed 12 real commits of garth (about 40,000 tokens of source per turn as Claude counts them) against the live Claude API (Sonnet 5.5, four cache breakpoints per request) and measured how much of each prompt the provider reused and what the replay cost.

File orderPredicted reuseMeasured reuseCost of the 13 turns
Krypton (most stable first)73%71%$0.51
Alphabetical48%47%$0.79
Reverse (most volatile first)0%0%$1.30

Excluding the first turn, which can never hit the cache. Including it, Krypton's order reused 65.7%. Krypton's order made the replay about 35% cheaper than alphabetical order. With a single cache breakpoint at the end of the prompt, every order reused 0%, so the ordering only pays when the stable files sit in front of earlier breakpoints. Predictions come from the shared prefix of consecutive prompts and landed within about two points of the live numbers.

Does it hold on other repositories?

Not always. We ran the same replay on a second repository, pluggy, against the live Claude API, and Krypton's order did worst:

File orderPredicted reuseMeasured reuse
Krypton (most stable first)4%4%
Alphabetical23%22%
Reverse (most volatile first)26%25%

(The reverse run stopped early at the spending cap, so its figure covers only the first eight replay turns.) The history ranked one file as the most stable, and it then changed in 3 of the next 12 commits, and a refactor added and renamed files. A change early in the order throws away most of the cache. The prediction matched the live result within a point, on garth and on pluggy, so we used it to survey 20 repositories without spending anything on live runs. What to expect. The ordering helps when the files that changed often recently keep changing, and the files that were quiet stay quiet. It can hurt after a refactor or a change in what the team is working on. We tried changing how the history is weighed (recent changes counting more, shorter windows, size of change) and choosing a rule per repository from its own earlier history; none of it improved results reliably on repositories it had not been tuned on, so the ordering is unchanged. The best way to know is to check your own repository: replay its recent commits with the research tool in krypton/tools (python -m tools.cache_anthropic REPO --dry --no-control prints the predicted reuse for each order and costs nothing).

Projected savings for a team

This is a model, not a measurement of your bill. It takes a team of 50 developers, each sending 100 agent requests a day for 22 days a month, over a 25,000-line repository (about 287,000 tokens each time the code is read), at list prices. It counts only the cost of re-reading the code on every request. Two measured effects are applied: Krypton's file order (the reuse rates below) and the cheaper later changes after a cleanup, which averaged 16.9% over six runs on garth.

Where the rates come from. The reuse rates are what was measured on the live Claude API on garth (71% of each request reused with Krypton's order against 47% alphabetical), and the cleanup saving is the average of six runs there. Results depend on your repository's history. Applying the cleanup saving to the whole monthly bill is an assumption, and the cleanup itself costs about $0.48 once on garth.

Refactoring and the payback

A Krypton-guided refactor of garth took the logic-complexity flags from 9 to 0 with all 163 tests passing, where an unguided refactor left 8 of 9. We then asked whether the cleaned code is cheaper for an agent to change. Fresh agents made the same five change tickets on the original code and after each of two cleanups, six runs each (three with unrelated tickets, three revising one feature), with real token usage priced at list prices:

  • Cleaning everything cost $0.48 once and made each later change 16.9% cheaper on average, but the typical run saved about 6% (runs: 44%, 7%, 5%, 25%, 0%, 1%).
  • Cleaning only the often-changed, tangled files (chosen from git history) cost $0.27 and saved 8.0% on average (runs: 26%, 14%, −17%, 20%, 0%, −12%).
  • On the averages, cleaning everything pays for itself after about 66 changes and the hot-files option after about 79, but run by run it ranged from 18 to never changes.
  • Without a cleanup, one feature kept compounding: after five revisions its main function was about 457 times over Krypton's limit, from 46 times at the start. With a cleanup first it stayed between 5 and 37 times over.
  • Rebuilding garth worst-function-first until Krypton scored it 81 (from 62) left the cost of the same five later revisions unchanged in one run ($0.176 against $0.177).

Read these as estimates. Six runs on one repository, one model and one cache model. The caching gap is large; the cleanup saving is not: it ranged from −17% to 44% between runs, so the 66-change payback is a range, not a number. The cleaned code was also not more correct (28 of 30 tickets right after clean-everything and 29 of 30 after hot-files-only, against 30 of 30 with no cleanup), and an earlier test of three tickets over ten repetitions found no saving at all after a refactor.

A CI gate over twenty revisions

We also tested Krypton as a check in CI. One feature of garth grew over 20 sequential revisions made by an agent, three times with each setup. In the plain setup the agent just did each ticket. In the gate setup the harness scored the code with Krypton after each ticket, and if a function the ticket touched was over the structure limit, an agent was sent back with Krypton's report to fix it before the next ticket. Neither agent was given the Krypton tool or told to refactor.

PlainWith the gate
Cost of 20 revisions$0.92$1.49 (+62%)
Worst function at the endabout 1,900× over the limitabout 12× over
Structure score at the end5572
Revisions done correctly60 of 6060 of 60

The gate kept the code far healthier, at a cost of about 62% more per chain, most of it the fix rounds. Cost per revision did not keep rising with the tangle: in the plain chains it rose about 30% over the first ten revisions and then stayed flat while the worst function grew from about 56× to about 1,900× over the limit. So within 20 revisions we found no saving from cleaner code, and the case for it rests on the people who read the code and on future risk, which we did not measure.
