7 · Method and formulas

The ordering only arranges files; it never changes a complexity score.

  • Volatility orderfiles are sent from least to most frequently changed, using Krypton's ordering algorithm over the repository's change history, so the stable part of the prompt stays at the front.
  • Cached sharecached_tokens ÷ prompt_tokens, read from the provider's usage fields, replayed commits 1–12 (turn 0 is a cold start and can never hit).
  • Predicted sharelongest common prefix of two consecutive prompts ÷ prompt length, rounded down to the provider's 128-token steps (cache starts at 1,024 tokens). Matched the live result within about 2 points.
  • Bill ratio1 − (1 − k) · h, where h is the reused share of each request and k is the cached-read price as a fraction of the normal input price.
  • Per-change savingtokens an agent spent on three identical change tasks, original vs refactored: 2,145 fewer of about 40,400 per change (5.3%).
  • Paybackone-time refactor cost ÷ per-change saving = 101,398 ÷ 2,145 ≈ 47 change tasks. Net tokens saved after n changes = 2,145 · n − 101,398; return on total spend = that ÷ (40,400 · n).

Summary

  • CachingKrypton's file order kept 79% of prompt tokens cached, against 58% alphabetical and 1% reverse.
  • RefactorLogic-complexity flags went from 9 to 0 with all 163 tests passing; the control agent left 8 of 9.
  • Payback47 change tasks repay the one-time refactor (101,398 tokens). After that, every change costs 5.3% fewer tokens.
  • CostThe refactor used 2.4× the tokens of a no-Krypton refactor and left the code the same size.
