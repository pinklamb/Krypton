Krypton benchmark

Does Krypton help on a real AI-written codebase?

Tested on garth, an MIT-licensed Garmin client where 163 of the last 225 commits carry an AI co-author trailer. Prompt caching was measured live on OpenAI through OpenRouter; the refactor and the change tasks were done by Sonnet agents, with garth's own 163 tests as the check.

1 · Prompt caching: does Krypton's volatility order work?

The whole src/ (~25K tokens) was sent as one prompt per turn while replaying garth's last 12 real commits. Krypton ordered the files from commit history before the replay, stable files first. OpenAI caches the longest repeated prefix, so edits to files near the end leave most of the prompt cached.

2 · Refactor: what did Krypton change in the code?

Two agents refactored identical copies of garth under the same rules. One had Krypton in the loop; the control did not, and stopped when it judged the code clean. All 163 tests pass in every copy.

The 5 flags Krypton left are hub files (__init__.py, http.py, utils.py, data/_base.py) flagged for coupling. The agent chose not to split them.

3 · Change tasks: is the refactored code cheaper to modify?

Fresh agents made the same three changes on the original and on the Krypton-refactored garth, without knowing about Krypton. Every result passed the hidden acceptance tests (14 of 14 per arm) and the full existing suite.

Show data table

4 · Does the refactor itself make caching easier?

The same 39 real function-level edits (from the last 12 commits) were applied to both layouts. Whatever Krypton split, the volatile files stayed put: version.py, http.py and __init__.py are the hubs it left alone.

Result: no difference. Both layouts predict the same cached share under every order. The live check on the original layout (78% and 53%) is within 2 points of the prediction, as in section 1.

6 · Method and formulas

Every figure on this page comes from one of these definitions. The volatility index only orders files; it never changes a complexity score.

  • Volatility indexcommits touching file ÷ commits touching the busiest scanned file (last 200 commits). Uncommitted or new files = 1.0. Files are sent stable first, ties broken by name.
  • Cached sharecached_tokens ÷ prompt_tokens, read from the provider's usage fields, replayed commits 1–12 (turn 0 is a cold start and can never hit).
  • Predicted sharelongest common prefix of two consecutive prompts ÷ prompt length, rounded down to the provider's 128-token steps (cache starts at 1,024 tokens). Matched the live result within about 2 points.
  • Bill ratio1 − (1 − k) · h, where h is the reused share of each request and k is the cached-read price as a fraction of the normal input price.
  • Per-change savingtokens an agent spent on three identical change tasks, original vs refactored: 2,145 fewer of about 40,400 per change (5.3%).
  • Paybackone-time refactor cost ÷ per-change saving = 101,398 ÷ 2,145 ≈ 47 change tasks.

7 · Reproduce

The command-line tool and Python package are still named argon. Keys are read from the environment or a git-ignored .env file; nothing is printed or stored.

# predicted cache share per file order, no API calls
$ python argon/tools/cache_live.py <repo> --subdir src --turns 12 --dry

# live replay against the cache model (spends credit; asks first)
$ python argon/tools/cache_live.py <repo> --subdir src --turns 12 --model openai/gpt-4.1-nano

# the file order Krypton would send, most stable first
$ python -m argon.cli <repo>/src --order-by-volatility

Limits

  • One repo, one cache model, one run per arm. The caching gap is large enough to trust; the 5% task saving is within the noise seen between runs.
  • The refactor spent 101K tokens, 2.4× the control, and the code is no smaller in tokens (24,720 → 24,622). At about 2.1K saved per task it takes roughly 47 change tasks to recoup that in tokens.
  • Krypton found the heavy code and kept the agent working until the logic flags were gone. The control touched two files and left the 46× outlier alone. A stricter control prompt might close part of that gap.
  • Code in the snippet dataset was never executed, so those refactors are not verified to behave the same.
  • Token counts for agents come from the harness and likely exclude cache reads. Only sections 1 and 4 read provider cache fields; section 1 is live and section 4 is mostly predicted from prefix math.
