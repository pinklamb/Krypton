Argon

Argon measures how structurally heavy code is: how many decisions it makes, how deeply they nest, and how much of it is packed into oversized functions. It reads JavaScript, TypeScript and Python, runs locally, and needs no network or account.

It is built for the loop where a coding agent writes code. After each change the agent runs Argon, sees which files and functions got heavy, and splits them before the weight costs tokens and invites mistakes. It is not a linter and does not judge correctness or style. Run your linter alongside it.

How it works

Every run follows the same steps:

  • Collect. Argon finds the source files, honoring .gitignore and skipping vendored and generated code.
  • Parse. Each file becomes a syntax tree. Files that cannot be parsed, or are too large to parse safely, are flagged instead of guessed at.
  • Measure. One pass over the tree records decisions, nesting, function boundaries and file wiring.
  • Rate and flag. Each function and file gets a rating, and files that cross a rule are flagged.
  • Score. The whole run gets a single purity score, and the command exits non-zero when it falls too low.

The scoring details are not published on this page.

Measurements

Branches
Counts the decisions in the code: conditions, loops, switch cases, error handlers, boolean operators and conditional expressions. It follows the conventions of established tools so numbers are comparable.
Nesting
Weighs a decision by how deeply it is buried. Code that branches inside branches costs more than the same number of flat branches. A function defined inside another is scored on its own, and its parent pays for it.
Effective lines
Measures size in a way packing cannot hide. Comments and blank lines do not count; long lines and lines with several statements count for more. Squeezing code onto fewer lines does not lower the size.
Refactoring hints
For each heavy or deeply nested function, Argon points at the deepest decision and the block worth pulling out, says how much of the function's weight that block holds, and gives one piece of advice for the function's shape: return early, use a lookup table, name the conditions, or split it into steps. Each names the effect it predicts. Hints never change a score.
Progress log
With a history file Argon records each run and compares it with the last: how the purity score moved, which heavy functions improved, and which have stalled. When a function is stuck it says why, for example that the block it was told to extract is untouched, or that the weight moved into another function instead of shrinking. The log holds numbers and hashes, never source text.
Strictness levels
The report says how many functions are over the limit and how far over the worst one is. --level sets how strict the limit is: relaxed to clear the worst offenders first, standard for the fitted limit, and strict for a tighter one. Nothing is saved between runs, so there is no baseline to reset.
Function ranking
Lists the heaviest functions in the run, with their location, so an agent knows exactly what to refactor first. Functions three or more levels deep carry a nested note.

Flags

Logic complexity
A file is flagged when its heaviest function combines many decisions with a lot of code. The fix is usually to split that function by job.
Concentration
A very large file that also has many asynchronous entry points is flagged as doing too much in one place.
Fragmentation
Flags the opposite problem: a group of files that import each other so heavily that the code has been shattered into pieces that cannot be understood alone. Four or more tiny files that all import each other count.
Overload checks
Rating-based checks can be diluted, for instance by giving every branch a different return value. So Argon also flags a function that makes too many decisions or nests too deeply, and a file whose total weight is over budget, however the code is laid out or split into helpers. These checks count decisions, not lines or return values.
Coupling hotspot
Flags a file that is wired to many others, through imports or through a shared global object that many scripts read from, as in browser code without modules. These are the files every feature ends up touching. The shared-global detection is a prototype and only covers JavaScript and TypeScript.
Not checked and unparseable
Files that are too big, contain extremely long lines (minified code), are not analyzed. They are left out of the score, never silently: the result lists each kind with a plain explanation and the setting that raises the limit so they can be checked. Files with too many syntax errors are flagged instead, since broken code should not pass.

Purity score

A single number from 0 to 100 for the whole run. It falls as more of the changed code sits in flagged files and as flagged files get heavier. Below a set level the check fails and the command exits with status 1, which is what lets it gate a pull request or stop an agent from finishing.

Overhead tax

Splitting code into many tiny functions can lower per-function numbers without making the code simpler. When most of a file's functions are trivial wrappers, Argon lowers the purity score a little. It is a warning that the structure is padded, not a flag, and files with few functions are never affected.

Changed lines only

With --base Argon scores only the lines that changed since a commit or branch, including new files. Old code in a touched file does not count against the change, so an agent is judged on what it wrote.

How prompt caching works

Model providers can cache the start of a prompt. When the next request begins with exactly the same text, the cached part is billed at a fraction of the normal input price and processed faster. Only the longest identical beginning counts: everything after the first changed character is processed and billed in full.

For code, this means the order of files matters when a tool sends the whole codebase each turn:

  • If a file that changes every turn sits near the top, almost nothing after it can be reused.
  • If stable files come first and volatile ones last, the long stable beginning stays identical from turn to turn and is reused.

Small, separate files help because a change touches fewer of them, and the untouched ones can form a long shared prefix. One huge file does not: an edit near its top invalidates the rest of it.

Limits. Many agent tools append to the conversation instead of re-sending files, so edits never invalidate the cache and ordering gains little. Providers expire caches after a short time. Argon's ordering is a hint from history, not a guarantee of savings.

Volatility order

Argon can measure how often each file changes, using recent git history or counts you supply, and print a list of files from most stable to most volatile with a rough size for each. A tool that builds prompts can concatenate files in that order. The ordering never changes a score.

argon src --order-by-volatility

Install and agents

pip install .          # Python 3.12+, run from the repo folder
argon src --top 10

# or with Docker
docker build -t argon .
docker run --rm -v "$PWD:/repo" argon .

To use it with a coding agent, add rules like these to CLAUDE.md, AGENTS.md or your tool's rules file:

## Code structure (Argon)
- After editing source files, run: argon <changed files or folders>
  --top 10 --history .argon/history.jsonl
- If a file is flagged, or a function you wrote shows a nested note,
  refactor it before finishing: early returns, small named helpers,
  one job per function.
- Do not satisfy Argon by packing code onto fewer lines or by splitting
  one function into many trivial wrappers.
- If a function is marked STALLED, do what its stated reason says
  before trying anything else.
- Re-run Argon after refactoring and report the purity score.
argon . --base origin/main    # score only what this branch changed
argon src --json              # machine-readable result for hooks and CI
Argon. Local, no network.
