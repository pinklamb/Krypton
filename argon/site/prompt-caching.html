Prompt caching

Cut the cost of re-reading your code

Coding agents send your codebase to the model on every turn. Providers bill text they have already seen at a fraction of the normal price, so the longer the unchanged part stays at the front of each request, the smaller the bill.

How caching rewards order

Providers cache the longest identical prefix of a request. If a file near the start changes, everything after it has to be read again at full price. If only files near the end change, almost the whole request is reused.

So the best order puts the files that rarely change first and the ones that change often last.

Krypton's ordering

$ krypton src --order-by-volatility
# JSON: files from most stable to most volatile, with a token estimate for each

Krypton's ordering algorithm uses each file's change history. Build your prompt from the files in that order. You can supply your own change counts with --volatility counts.json. The ordering is a hint from history, not a guarantee, and it never changes a score.

Measured results

We replayed 12 real commits of garth (about 25,000 tokens of source per turn) against a live model and measured how much of each prompt the provider reused.

File orderPredicted reuseMeasured reuse
Krypton (most stable first)81%79%
Alphabetical60%58%
Reverse (most volatile first)1%1%

Excluding the first turn, which can never hit the cache. Including it, Krypton's order reused 72.6%. Predictions come from the shared prefix of consecutive prompts and landed within about two points of the live numbers.

Refactoring and the payback

A Krypton-guided refactor of garth took the logic-complexity flags from 9 to 0 with all 163 tests passing, where an unguided refactor left 8 of 9. Fresh agents then made the same three changes on the original and the refactored code:

  • The refactored code used 5.3% fewer tokens per change (2,145 of about 40,400).
  • The refactor itself cost 101,398 tokens, about 2.4 times an unguided refactor.
  • So it takes about 47 change tasks to repay the refactor. After that, every change costs 5.3% fewer tokens.

Read these as estimates. One repository, one cache model and one run per arm. The caching gap is large; the 5.3% task saving is within run-to-run noise, so the 47-change payback is approximate.
